## 1- مقدمه

امروزه اطلاعات علمی و فنی اساس توانائی های مادی و معنوی جوامع بشری بوده و هر جامعه ای که بتواند به اطلاعات بیشتری دست یابد از توان و پویایی بیشتری نیز برخوردار خواهد شد. فناوری اطلاعات و ارتباطات به عنوان یکی از بسترهای نوین به سرعت در حال تأثیر گذاری بر زندگی بشر است و این تأثیر در کلیه وجوه اجتماعی دیده می شود. در عصر تکنولوژی، اطلاعات، بخش حیاتی برای ارائه مراقبت بهداشتی و درمانی است. سازمان تامین اجتماعی به عنوان سازمان پیشرو در اجرای طرح نسخه الکترونیک به عنوان هسته اصلی پرونده الکترونیک سلامت، بر آن است با استقرار پروتکل تبادل اطلاعات با سایر تولیدکنندگان نسخه الکترونیک گام های موثری در راستای تکمیل طرح مذکور برداشته شود.

این سند به منظور تشریح چگونگی ارسال نسخ الکترونیک تجویزی پزشک برای بیمه شده سازمان تامین اجتماعی می باشد. کلیه نرم افزارهای مطب دارای مجوز و گواهینامه های لازمه امکان بهره برداری از این سرویس را خواهند داشت.

## 2- سرویس احراز هویت

احراز هویت با روش **PKCE** صورت می گیرد که برای دریافت توکن از سرور، از یک مقدار که توسط کلاینت ساخته شده، استفاده می شود. در این روش یک کد جدید توسط کلاینت ساخته می شود و به همراه درخواست ارسال می شود. سپس دوباره authorization-code به سرور ارسال می شود تا اعتبار سنجی صورت گیرد. مراحل کلی درخواست به صورت زیر می باشد:

- ارسال درخواست جهت دریافت `authorization-code`
- ارسال درخواست برای دریافت `توکن`

### نحوه تولید code verifier و code challenge

کلاینت برای دریافت `authorization code` باید یک کد تولید کند. این کد `code verifier` نام دارد که رشته ای تصادفی است شامل 43 تا 128 کاراکتر و از ترکیب کاراکترهای `[A-Z]`, `[a-z]`, `[0-9]`, `-`, `.`, `_`, `~`.

**Code Verifier:**
- تعداد کاراکتر های مجاز: ۴۳ تا ۱۲۸ کاراکتر
- کاراکتر های مجاز: `[a-z]`, `[A-Z]`, `[0-9]`, `-`, `.`, `_`, `~`

**Code Challenge:**
زمانی که از `code verifier` ساخته شد، از آن برای ساخت `Code Challenge` استفاده می شود. این کد از طریق `hash` کردن آن با روش `SHA256` و سپس `encode` به روش `BASE64-URL-encoded` ساخته می شود.

```text
BASE64URL-ENCODE(SHA256(ASCII(code_verifier))) == code_challenge
```

با توجه به توضیحات بالا و نحوه تولید کدهای ذکر شده، از دو سرویس زیر جهت دریافت توکن استفاده می شود.

### 1-2- ارسال درخواست برای دریافت authorization_code

این سرویس باید با متد `GET` فراخوانی شود و باید به آدرس زیر درخواست ارسال گردد. با فراخوانی این سرویس خروجی، به شکل `html` خواهد بود و در واقع پزشکان به درگاه ورود کاربران سازمان تامین اجتماعی ارجاع داده می شوند تا گذرواژه و نام کاربری خود را وارد نمایند.

**آدرس محیط عملیاتی:**
```
https://account.tamin.ir/auth/server/authorize
```

**آدرس محیط تستی:**
```
https://account-pilot.tamin.ir/auth/server/authorize
```

پارامترهای زیر نیز به عنوان `QueryParam` باید اضافه گردند.

| پارامتر | توضیحات |
| :--- | :--- |
| `redirect_uri` | آدرس بازگشت سایت یا آدرسی که کاربر به این صفحه ارجاع داده خواهد شد. |
| `code_challenge` | این مقدار باید توسط کلاینت ساخته شود که در ادامه درباره آن توضیح داده شده است. |
| `client_id` | شناسه کلاینت که قصد دریافت توکن را دارد. |
| `response_type` | برای این پارامتر مقدار `code` تخصیص داده شود. |
| `code_challenge_method` | برای این پارامتر مقدار `S256` تخصیص داده شود. |

**نمونه فراخوانی سرویس به شکل زیر خواهد بود:**

```
https://account.tamin.ir/auth/server/authorize?redirect_uri=https://ep.tamin.ir/view/index.html&response_type=code&client_id=12345...12345a&code_challenge=VILZG3tR4MuMQXbySv7OQTmM•Ez4SrtV RoAiBaRvPLQ&code_challenge_method=S256
```

این آدرس پس از ساختن پارامترهای ذکر شده در مرورگر باز شود و با خروجی مشابه زیر مواجه خواهد بود. (تصویر زیر برای محیط تست می باشد.)

نهایتا پس از ورود پزشک و وارد کردن نام کاربری و گذرواژه، خروجی مشابهی در آدرس بازگشتی وارد شده خواهد داشت که مقدار `code` باید در سرویس بعدی ارسال شود.

```
http://{redirectUri}/?code=eyJhbGciOiJSUzI1NiI*******Fgerty2R&expires_in=60
```

**نکته:** جهت تشخیص کاربر فعلی که در حال استفاده است (یا هر داده دیگری که جهت تشخیص و تمایز بین کاربران یا سیستم‌های مختلف استفاده می شود) پارامتر `state` به ورودی‌های این سرویس باید اضافه گردد و عمل رد آن به این صورت می باشد که در آدرس بازگشتی علاوه بر پارامترهای دیگر این پارامتر نیز با همان مقداری که ارسال شده است قابل دریافت می باشد. به عنوان مثال اگر سرویس اول به صورت زیر فراخوانی شود:

```
https://account.tamin.ir/auth/server/authorize?redirect_uri=https://ep.tamin.ir&response_type=code&client_id=12345...12345a&code_challenge=VILZG3tR4MuMQXbySv7OQTmM0Ez9SrtVRo8iBaRvPLQ&code_challenge_method=S256&state=1234567891
```

پس از اتمام احراز هویت پزشک، در درگاه سامانه تامین اجتماعی، موقع بازگشت به آدرس بازگشتی به صورت زیر خواهد بود:

```
http://{redirectUri}/?code=eyJhbGciOiJSUzI1NiI*******Fgerty2R&expires_in=60&state=1234567891
```

### 2-2- دریافت توکن

در ادامه جهت دریافت توکن، باید وب سرویس زیر را با متد `POST` فراخوانی گردد. در فراخوانی این سرویس ورودی ها باید به صورت `x-www-form-urlencoded` ارسال گردد.

**آدرس محیط عملیاتی:**
```
https://account.tamin.ir/auth/server/token
```

**آدرس محیط تستی:**
```
https://account-pilot.tamin.ir/auth/server/token
```

**پارامترهای ورودی:**

| پارامتر | توضیحات |
| :--- | :--- |
| `redirect_uri` | |
| `grant_type` | باید با رشته `authorization_code` ارسال گردد. |
| `client_id` | |
| `code` | کد دریافت شده در سرویس قبل که به آن اشاره شد. |
| `code_verifier` | مقدار ساخته شده که طریقه ساخت آن توضیح داده شد. |

خروجی سرویس همان توکن خواهد بود و توکن جهت استفاده در سایر سرویس‌ها مورد استفاده می‌باشد.

```json
{
  "access_token": "eyJhbGciOiJSUzI\NiJ9.dWliOiIwftTUxq\RdefWIgCNDUxM....",
  "expires_in": 3600
}
```

با استفاده از این دو سرویس شرح داده شده، امکان دریافت توکن وجود دارد. جهت دریافت توکن با قابلیت `refresh` (در بخش [1-4-2](#1-4-2-سرویس-تجدید-توکن-پزشک) پس از سرویس تجدید توکن پزشک) و در ادامه سرویس دریافت توکن با استفاده از `refresh token` (بخش [2-4-2](#2-4-2-سرویس-دریافت-توکن-جدید-با-استفاده-از-refresh_token)) استفاده گردد.

### 3-2- سرویس خروج از سامانه

از این سرویس جهت خروج از سامانه نسخه نویسی تامین اجتماعی استفاده می شود و باید زمانی که کاربر قصد خروج از سیستم را دارد فراخوانی گردد. نحوه فراخوانی این سرویس به این شکل می باشد که آدرس بازگشتی اعلام شده را به عنوان ورودی دریافت می کند و با متد `GET` باید فراخوانی گردد.

**آدرس محیط عملیاتی:**
```
https://account.tamin.ir/auth/signout?redirect_uri=https://ep.tamin.ir
```

**آدرس محیط تستی:**
```
https://account-pilot.tamin.ir/auth/signout?redirect_uri=https://ep.tamin.ir
```

**پارامترهای ورودی:**
- `redirect_uri`: آدرسی که به عنوان آدرس بازگشتی توسط شرکت اعلام شده است.

#### 1-4-2- سرویس تجدید توکن پزشک

پس از فراخوانی سرویس اول (دریافت `authorization code`) جهت تجدید توکن یا استفاده از `refresh token`، باید سرویس زیر با پارامترهایی که در ادامه آمده است فراخوانی گردد. سرویس با متد `POST` باید فراخوانی گردد.

**آدرس سرویس در محیط عملیاتی:**

```
https://account.tamin.ir/auth/server/v2/token
```

**آدرس سرویس در محیط تست:**
```
https://account-pilot.tamin.ir/auth/server/v2/token
```

#### 2-4-2- سرویس دریافت توکن جدید با استفاده از refresh_token

در ادامه جهت دریافت توکن جدید بدون نیاز به ارجاع پزشک به صفحه ورود، باید سرویس زیر با پارامترهای قید شده با متد `POST` فراخوانی گردد. نحوه ارسال اطلاعات در سرویس قبل و این سرویس باید با فرمت `x-www-form-urlencoded` باشد.


**آدرس سرویس در محیط تست:**
```

```

**پارامترهای ارسالی:**

| پارامتر | توضیحات |
| :--- | :--- |

| `client_id` | |

| `audience` | اطلاعات فرد یا موجودیتی که برای وی توکن صادر میگردد، مانند کد ملی پزشک. |

### نکات مهم در فراخوانی سرویس ثبت نسخه الکترونیکی

1.  سه قلم اطلاعاتی `docId`، `docNationalCode` و `docMobileNo` صرفا جهت کنترل های مرتبط با احراز هویت پزشک ثبت نام شده می باشد و لذا نیاز است حتما با اطلاعات وارد شده هنگام ثبت نام پزشک مطابقت داشته باشد.
2.  جهت ثبت نسخه دارویی با دوره تکرار، علاوه بر ارسال دوره تکرار (`repeat`)، باید تاریخ انجام (`dateDo`) ارسال شود. تکرار نسخه به این صورت خواهد بود که نسخه به تعداد دوره تکرار و به فاصله زمانی تاریخ امروز و تاریخ انجام (ارسال شده از طریق سرویس) تکرار خواهد شد. به عنوان مثال اگر تاریخ امروز `14030730` و تاریخ انجام `14040610` و دوره تکرار 2 ارسال شود، نسخه برای تاریخ‌های `1403/10/20` و `1403/11/20` نیز تکرار خواهد شد. توجه داشته باشید فرمت ارسالی تاریخ انجام، باید به صورت رشته با طول هشت کاراکتر (همانند تاریخ نسخه، مانند `14040610`) باشد و امکان تکرار بیشتر از 3 دوره وجود ندارد. همچنین جهت ثبت نسخه پاراکلینیک در صورتی که تاریخ موثر برای خدمتی وارد شود (همان فیلد `dateDo`)، پس از آن تاریخ امکان اقدام بر روی آن خدمت در مراکز پاراکلینیک وجود دارد.
3.  در نسخ فیزیوتراپی امکان مشخص کردن نوع بیماری و طرح درمان نیز وجود دارد، که باید شناسه مربوط به هر کدام ارسال شود. امکان دریافت شناسه هر کدام از طریق سرویس مربوطه که در لیست سرویس های پایه قرار دارد، میسر است.
4.  در نسخ دندانپزشکی برای دریافت "نوع خدمت دندانپزشک پزشکی" بیمار از فیلد `isDentalService` استفاده شده است که به صورت رشته (`String`) با محدوده مقادیر 0 یا 1 ارسال میگردد. مقدار "1" مربوط به خدمتهایی است که مشخصا برای یک دندان انجام شده است و مقدار "0" مربوط به خدمتهایی است که به دندان شماره خاصی وابسته نیستند و می‌توانند به کلیه دندان‌ها تعلق گیرند. در صورتی که پارامتر `isDentalService` ارسال نشود و سرویس وابسته به دندان خاصی باشد، ثبت نسخه امکان پذیر نخواهد بود. در صورتی که سرویس وابسته به دندان خاصی باشد، کد `FDI` آن دندان در قالب فیلد `toothId` بایستی ارسال گردد. در زیر نمونه داده برای ثبت نسخه دندانپزشکی آمده است.

5.  در نسخ پاراکلینیکی در صورتی که فیلد ترمینولوژی ارسال شود و مقدار آن برابر با `thritha.BEHDAISHT` باشد، کد خدمتی که ارسال می شود باید بر اساس کدینگ اعلامی وزارت بهداشت باشد و در صورتی که این فیلد ارسال نشود، بررسی و ثبت نسخه همانند روال سابق و کدینگ اعلامی از سمت سازمان پیش خواهد رفت.
6.  در نسخ ارجاعی، تاریخ ارجاع نشان دهنده مدت اعتبار نسخه ارجاعی می باشد که باید بین یک روز بعد از تاریخ جاری تا حداکثر 3 ماه بعد باشد. (بعد ازاین تاریخ حتی درصورت که بازخورد ارجاع ثبت نشده باشد این نسخه قابل ارجاع نخواهد بود) لازم به ذکر است حداکثر تعداد ارجاع 3 می باشد.
7.  به این نکته مهم توجه داشته باشید که تفاوت نسخه ارجاع با نسخه خدمات ارجاعی در این مورد می باشد که در نسخه ارجاع پزشک بیمار را با ارائه توضیحات به پزشک متخصص دیگری ارجاع می دهد و در واقع نظر وی را جویا می باشد. اما در نسخه خدمات ارجاعی، پزشک خدمت خاصی را برای وی انتخاب می کند که باید توسط پزشک دیگری صورت گیرد و امکان انجام آن خدمت پزشکی برای وی وجود ندارد. در صورت ثبت نسخه ارجاعی (`prescType=7`)، می بایست اقلام اطلاعاتی `noteDetailsReferralList` ارسال گردد.

### 1-9- سرویس بررسی قواعد دندانپزشکی

این سرویس باید با متد `POST` فراخوانی گردد. هدف از این سرویس بررسی قوانین و تعرفه های دندانپزشکی جهت تعیین امکان یا عدم امکان پرداخت به پزشک می باشد.

```
https://ep-test.tamin.ir/api/v2/check-rules-in-detail
```

جهت فراخوانی این سرویس بایستی کد خدمت، به همراه نوع آن مطابق آنچه در ثبت نسخه انجام می گردد، به عنوان پارامترهای اصلی ارسال شوند و برخی پارامترهای دیگر که در ادامه توضیح داده خواهند شد جهت تکمیل داده های ورودی سرویس اضافه گردند. ورودی یک `object` از کلاس `DentistRule` میباشد. در صورتی که سرویس وابسته به دندان خاصی باشد بایستی کد `FDI` آن دندان در قالب فیلد `toothId` ارسال گردد. در صورتی که خدمت انتخاب شده مربوط به رادیوگرافی باشد، آن تعداد از خدمتهایی که تا قبل از آن به نسخه جاری اضافه شده اند جهت بررسی کلیشه مشترک با خدمت جاری بایستی به ورودی سرویس ارسال گردند. این مجموعه خدمتها در قالب لیستی از کلاس `GridData` ارسال می شوند. برای سایر خدمات، پر بودن یا خالی بودن `GridData` در ورودی اهمیتی ندارد.

### 2-9- سرویس های پایه مربوط به دندانپزشکی

در ثبت نسخه های دندانپزشکی، بر اساس نوع خدمت دندانپزشکی یکی از دو سرویس زیر جهت نمایش خدمت های قابل ارائه، فراخوانی می شود.

**نوع خدمت دندانپزشکی با این دامنه در سیستم تعریف شده است:**
1.  خدمات و مراقبت های سلامت با کد `1`
2.  خدمات دندانپزشکی با کد `2` (خدمات رادیوگرافی از جمله بایت وینگ و پری اپیکال در این دسته خدمت قرار می گیرند.)

#### 1-2-9- سرویس اول

در صورتی که نوع خدمت `1` انتخاب شود، لیست خدمات قابل ارائه از طریق وب سرویس زیر فراخوانی می شود. با فراخوانی این سرویس دندانپزشک می تواند لیست خدمات مرتبط با مراقبت های سلامت دندان و رادیوگرافی را دریافت کند. این سرویس با متد `GET` باید فراخوانی گردد.

**آدرس وب سرویس عملیاتی:**
```
https://soa.tamin.ir/interface/epresc/SendEpresc/v2/find-dentist-service-name-without-tooth/{dentistType}
```

**آدرس وب سرویس تستی:**
```
https://ep-test.tamin.ir/api/v2/ws-dentist-base/find-dentist-service-name-without-tooth/{dentistType}
```

**ورودی های این سرویس عبارتند از:**
- `dentistType`: نوع خدمت دندانپزشکی (که برای خدمات و مراقبت های سلامت کد `1` می باشد).

#### 2-2-9- سرویس دوم

در صورتی که نوع خدمت `2` انتخاب شود، لیست خدمات قابل ارائه از طریق وب سرویس زیر فراخوانی می شود. با فراخوانی این سرویس دندانپزشک می تواند لیست خدمات مرتبط با یک دندان خاص را دریافت کند. (که شامل خدمات رادیوگرافی نیز می باشد). این سرویس با متد `GET` باید فراخوانی گردد.

**آدرس وب سرویس عملیاتی:**
```
https://soa.tamin.ir/interface/epresc/SendEpresc/v2/find-dentist-service-name-by-tooth/{selectedTooth}/{patientId}/{toothType}
```

**آدرس وب سرویس تستی:**
```
https://ep-test.tamin.ir/api/v2/ws-dentist-base/find-dentist-service-name-by-tooth/{selectedTooth}/{patientId}/{toothType}
```

**پارامترهای ورودی:**

## 16- نکات مهم

- برای ارسال نسخ پزشکان، هر پزشک میبایست حتما پس از ارسال نسخ آن در سامانه نسخه الکترونیک (`EP.TAMIN.IR`) در قسمت ثبت نام پزشکان، ثبت نام و تایید شده باشند.
- برای انجام عملیات پیاده سازی و تست نیاز است `client_id` به مسئول فنی شرکت منتخب تحویل گردد. همچنین شرکت باید آدرس بازگشتی (`redirect url`) خود را اعلام نمایند.
- تاریخ نسخه نمی تواند از تاریخ روز بزرگتر باشد.
- اگر نوع نسخه ویزیت باشد (`prescTypeId=3`)، `noteDetailEprscs` (اقلام نسخه) نباید دارای مقدار باشد، در غیر این صورت پیغام خطای "امکان انتخاب خدمات با توجه به نوع نسخه ی انتخابی وجود ندارد" نمایش داده می شود.
- اگر نوع نسخه دارو باشد (`prescTypeId=1`)، فیلد `srvType` باید برابر با `01` باشد، در غیر این صورت پیغام خطای "به نوع نسخه ی انتخابی تنها امکان انتخاب دارو وجود دارد" نمایش داده می شود.
- اگر نوع نسخه پاراکلینیک باشد (`prescTypeId=2`)، فیلد `srvType` باید برابر با یکی از مقادیر `02` تا `21` باشد (لیست کامل در ساختار `ServiceType` آمده است).
- کدملی و شماره تلفن همراه پزشک باید با اطلاعاتی که زمان ثبت نام در سامانه پزشکان ثبت شده است مطابقت داشته باشد، در غیر این صورت پیغام خطای "کدملی/ تلفن همراه پزشک معتبر نمی باشد" نمایش داده می شود.
- زمانی که اطلاعات دریافتی خالی باشد، پیام خطای "data is null خطا در اطلاعات ورودی" نمایش داده می شود.
- در صورتی که فیلد موبایل (`mobile`) خالی باشد، پیام خطای "شماره تلفن همراه وارد نشده است" نمایش داده می شود.
- در صورتی که فیلد موبایل (`mobile`) با الگوی درست وارد نشده باشد، پیام خطای "شماره تلفن همراه به درستی وارد نشده است" نمایش داده می شود.
- در صورتی که فیلد کد ملی بیمار (`patient`) معتبر نباشد، پیام خطای "کد ملی بیمار معتبر نمی باشد" نمایش داده می شود.
- در صورتی که فیلد `srvcode` معتبر نباشد، پیام خطای "کد خدمت + srvcode + تعریف نشده است" نمایش داده می شود.
- در صورتی که فیلد `prescTypeId` خالی باشد، پیام خطای "نوع نسخه انتخاب نشده است" نمایش داده می شود.
- در صورتی که فیلد `prescTypeId` یکی از موارد ذکر شده در سند نباشد، پیام خطای "نوع نسخه بدرستی وارد نشده است" نمایش داده می شود.
- در صورتی که اطلاعات نسخه شامل کد ملی بیمار، شماره نظام پزشکی پزشک، تاریخ نسخه، نوع نسخه و اقلام نسخه تکراری باشد، پیام خطای "نوع نسخه تکراری است" نمایش داده می شود.
- در صورتی که فرمت تاریخ نسخه درست نباشد، پیام خطای " تاریخ به درستی وارد نشده است" نمایش داده می شود.
- در صورتی که تاریخ نسخه بزرگتر از تاریخ روز باشد، پیام خطای "تاریخ نسخه نمی تواند از تاریخ روز بزرگتر باشد." نمایش داده می شود.
- در صورتیکه فیلد `drugAmntId` به درستی وارد نشده باشد، پیام "مقادیر مصرف صحیح وارد نشده است" نمایش داده می شود.
- در صورتی که فیلد `drugInstId` به درستی وارد نشود، پیام "زمان مصرف صحیح وارد نشده است" نمایش داده می شود.
